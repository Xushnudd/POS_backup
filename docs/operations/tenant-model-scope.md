# Tashkilot doirasidagi ma’lumotlar

Har bir Prisma modelining egaligi `src/server/auth/tenant-models.ts`da ochiq belgilangan: tashkilotning o‘zi, majburiy `organizationId`, ota-resurs orqali tashkilot yoki alohida vakolat talab qiladigan umumiy model. Umumiy foydalanuvchi identifikatori bir nechta tashkilotga a’zo bo‘lishi mumkin; tarif, retention va autentifikatsiya modellari tenant biznes jadvali sifatida avtomatik ochilmaydi.

`tenantScope` child modellarga ota-resursning filial va kassir cheklovlarini ham uzatadi. Noma’lum yoki umumiy model `UNSCOPED_MODEL` bilan rad etiladi. Scoped ORM insert/upsert uchun tashkilot kaliti yoki ruxsatli ota-resursni tekshiradi. Transaction service’lar `assertLiveContext` orqali joriy sessiya/vakolatni tekshirishda davom etadi. Raw SQL va fayl/worker/report yo‘llari o‘z explicit tenant parametrlarini saqlaydi; ORM extension raw SQL uchun RLS o‘rnini bosmaydi.

129 migration barcha scoped jadvallarga egalikni boshqa tenantga ko‘chirishni taqiqlaydigan guard va deferred FK-edge guard qo‘shadi. Native `pg_constraint` inventari ORMda ko‘rsatilmagan SQL FKlarni ham tekshiradi. Deferred guard transactionning yakuniy yozuvini o‘qiydi: bir transactionda yaratilgan-keyin o‘chirilgan yozuv yoki deferred ota-resurs bilan biznes operatsiya noto‘g‘ri rad etilmaydi. Global actor/konfiguratsiya havolalari alohida service authorization talab qiladi, ular boshqa tenant biznes resursiga havola sifatida talqin qilinmaydi.

131 migration Organizationning keraksiz deferred edge eventini olib tashlaydi; uning identity guardi qoladi. 132 migration native composite tenant FK bilan allaqachon isbotlangan havolani ikkinchi marta qidirishni kamaytiradi. Qolgan parent/reference lookup `FOR KEY SHARE` ishlatadi: oddiy narx tahririni to‘sadigan to‘liq row-share lock kerak emas. Yangi model/FK qo‘shilganda registry, native inventory test va migration preflight qayta ko‘rib chiqilishi shart.

Preflight eski ma’lumotni tuzatib yubormaydi: bo‘sh tenant root yoki cross-tenant FK topilsa migration to‘xtaydi. Katta legacy dataset uchun SQL set-based tekshiruv ishlatiladi. SKU/asosiy barkod/alias bir tenant ichida unique; boshqa tenant ayni qiymatni ishlatishi mumkin. Dublikatni yo‘qotish yoki katalogni avtomatik birlashtirish yo‘q.

Qabul protokoli: `scripts/ops/test-migration-dataset.sh` — alohida UUID bazalarda eski init datasetning haqiqiy dump/restore clone’i, 132 migration, original hash/ledger saqlanishi, fresh install, constraint validation va old backupga rollback. `tenant-catalog-acceptance.sql` ikki tenant va primary/alias collisionni tekshiradi. `tests/tenant-models.*.test.ts` barcha native modellarning guard qamrovi, scope/insert, cross-parent va concurrency testlarini beradi. Real mijoz bazasi, staging va production qabul sinovi ushbu lokal rehearsal bilan almashtirilmaydi.
