# Nazoratli yangilash va texnik xizmat

Operatorga tegishli doimiy katalogda `deployment.json` saqlang; katalog group/world-writable bo‘lmasin. Fayl ilova va worker foydalanuvchisiga o‘qiladigan, faqat operatorga yoziladigan bo‘lsin (odatda0640 va mos owner/group). Barcha app/worker instancelarga shu **katalog**ni read-only mount qiling; bitta fayl mounti atomic rename bilan yangi inodega o‘tishni ko‘rmasligi mumkin. `POS_DEPLOYMENT_STATE_FILE` mutlaq yo‘lni ko‘rsatadi. Bunday path sozlanmasa maintenance o‘chiq. Path sozlangan, lekin fayl yo‘q/buzilgan/xavfsiz emas bo‘lsa yangi durable amallar va worker claimlar fail-closed to‘xtaydi.

Fayl formati:
```json
{"maintenance":false,"message":"Xizmat ishlayapti"}
```
Ixtiyoriy `expectedEndAt` — offsetli ISO vaqt; taxminiy tugash, kafolat emas. Message3–500belgi, fayl4KiBdan oshmaydi; kutilmagan maydon rad etiladi. Fayl/yo‘l/credential APIga chiqmaydi. `/api/deployment/status` faqat holat, foydalanuvchi xabari va xavfsiz release identifikatorini beradi.

1. Operator xabar va oynani belgilaydi, faol kassirlarga xabarni ilovada ko‘rsatadi. `node scripts/ops/set-maintenance.mjs /absolute/operator/deployment.json on "Rejalashtirilgan yangilash"` atomic fsynced rename orqali holatni yoqadi.
2. Yangi `runOperation` orqali moliyaviy/ombor/core amallari503 `MAINTENANCE`, `Retry-After:30` oladi. Allaqachon admissiondan o‘tgan amal tugashi mumkin. Oldin commit bo‘lgan aynan shu actor/payload/key qayta so‘rovi fresh authorizationdan keyin eski natijani qaytaradi. Yangi urinish hech qanday Operation yoki business posting yaratmaydi. Lokal IndexedDB basket/queue o‘chirilmaydi. Non-durable katalog/account management CRUD uchun alohida release discipline va tashqi operator nazorati kerak; bu switch barcha HTTP yozuvlarni avtomatik bloklaydi deb hisoblamang.
3. Readiness503 bo‘ladi; liveness ishlab turadi. Supervisor yangi trafficni readinessga qarab ajratadi. Job worker keyingi cycle claimlarni pauza qiladi; allaqachon boshlangan cycle/ish tugaydi. Worker PID/SIGTERM/graceful timeoutni mavjud supervisor bilan kuzating. DB migratsiyasidan oldin active transactionlar tugaganini operator tekshiradi. Barcha instancelarda umumiy file mount va pool/readiness routing hostda tasdiqlanishi kerak.
4. Encrypted backup/manifest va restore tekshiruvini bajaring; expand-contract migratsiya va avvalgi/yangi payload compatibilityni saqlang. Destructive migrationni rollback deb avtomatik o‘chirmang. Pending/offline lease va original operation keysni yangi versiya o‘qiy olishi shart.
5. Immutable image/release bilan yangilang. Next16.3.8 local guide bo‘yicha **build va runtime uchun bir xil** `NEXT_DEPLOYMENT_ID` bering; bir release instancelari shu identifikatorni ishlatsin. NextdeploymentId eski/yangi asset skewni aniqlaydi, lekin requestlarni mos releasega host/CDN yo‘naltiradi. Kesh yoki fileflag buning o‘rnini bosmaydi. Ilova server release o‘zgarishini xabar qiladi; savat/navbatni tekshirib qayta ochish kerak, lokal navbatni tozalash kerak emas.
6. Readiness/migration va smoke to‘g‘ri bo‘lgach `node scripts/ops/set-maintenance.mjs /absolute/operator/deployment.json off "Yangilash tugadi"`. Kutilayotgan amallar **asl** kalit bilan sinxronlanadi, qoralama to‘lov davom ettiriladi. Committed sale qayta sotilmaydi. Open basket narxi/solig‘i serverda yangidan tekshiriladi; ziddiyatni yashirmang.

Isolated test: dedicated `/tmp/pos-maintenance-e2e-state.json` va `NEXT_DEPLOYMENT_ID=pos-maintenance-20261009` bilan production HTTPS three-browser scenario saved basket→maintenance503pending→reload→original sync→cash completionni tekshiradi. Bu real hostdagi rolling deploy, external routing yoki SLA tasdig‘i emas.

Nativeimage app UID/GID1001; hostdagi katalog/fayl read permissionini shunga mos operator boshqaradi. Faylni app yozmaydi. Basecompose overlay qo‘shilmaguncha odatdagi ish tartibini saqlaydi.
