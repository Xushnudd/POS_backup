# TOTP shifrlash kalitini almashtirish

Bu operator CLI jarayoni, HTTP endpoint emas. Real kalit o‘zgartirish yoki productionga qo‘llash ushbu implementatsiya bilan avtomatik bajarilmaydi. Kalitlar inherited deployment environment/private secret store orqali beriladi; argument, kod, audit yoki logga ochiq yozilmaydi.

1. Joriy kalit va zarur eski kalitlarni secret managerda xavfsiz saqlang; alohida encrypted secret recovery backup tartibidan foydalaning. Barcha instance/workerlar yangi `AUTH_CHALLENGE_SECRET` va eski kalit(lar)ni `AUTH_TOTP_PREVIOUS_SECRETS` (ko‘pi bilan ikki) orqali ko‘ra oladigan qilib kelishilgan rolling deployment tayyorlang. Yangi enrollment faqat yangi kalit bilan yozadi. Old key overlap faqat TOTP decryption uchun; boshqa SMS/e-mail challenge pepper/delivery materialiga umumiy fallback bermaydi.
2. `npm run worker:build`. Operator muhitida `DATABASE_URL`, `POS_TOTP_ROTATION_CONFIRM_DATABASE` (URLdagi bazaning aynan nomi), `POS_TOTP_ROTATION_OPERATOR_ID` (faol platform_admin), `POS_TOTP_ROTATION_REASON` va ixtiyoriy UUID `POS_TOTP_ROTATION_BATCH_ID` sozlang. Bash xtrace, terminal historyga secret qiymat yozish yoki process argumentiga kalit qo‘yishdan saqlaning. CLI `.env` fayllarini qidirmaydi yoki avtomatik ochmaydi.
3. `npm run worker:totp-rekey -- --check`. Bu standart rejim, yozmaydi; faqat scanned/current/pending/absent/failed hisoblarini beradi. Noto‘g‘ri konfiguratsiya, DB nomi yoki grant bo‘lsa rad. Undecryptable envelope `failed` va nonzero exit beradi; credentiallar chiqmaydi.
4. Apply uchun operator-owned `POS_DEPLOYMENT_STATE_FILE` orqali **valid maintenance=true** yoqing, admitted ishlarni drain qiling. `npm run worker:totp-rekey -- --apply`. Har bir faktor alohida atomik tranzaksiyada: target/operator User lock, live platform grant shared lock, ciphertext tekshiruvi, immutable TotpKeyRotation provenance va sealedSecret-only update. Batchlar 100 tadan; vaqt/pool bosimi bounded. Pending yoki tasdiqlangan faol faktor ko‘chiriladi; revoked faktor ko‘chirilmaydi.
5. `--check` ni mustaqil qayta ishga tushiring. Faqat full check `pending=0` va `failed=0` bo‘lsa shu DB dagi barcha faol envelope joriy kalitga tegishli. Barcha eski instance/workerlar yangi kalit bilan yozayotganini, replica/backup va boshqa muhitlarning recovery talablarini ham tekshirmasdan old keyni olib tashlamang. CLI hech qanday environment/secret manager konfiguratsiyasini o‘zgartirmaydi. Apply chiqishi key-retirement approval emas.
6. Maintenance ni operator tartibida o‘chiring; asl authenticator bilan yangi proof, qayta code rad va recovery nazoratini stagingda tekshiring. Hozirgi kod buni local/test qabulda tekshiradi; real rollout alohida operator vazifasi.

Faktor ID, user binding, secretning ochiq qiymati, confirmedAt, lastCounter, attempts va recovery hashlar o‘zgarmaydi. Eski kod counter sabab qayta qabul qilinmaydi. Audit eski/yangi envelope SHA256 va target key fingerprint saqlaydi, ochiq kalit yoki ciphertext saqlamaydi. Audit/source update xatosi ikkala yozuvni qaytaradi. Qayta ishga tushirilgan yoki parallel CLI oldindan ko‘chirilgan envelopega yozmaydi; interrupted applydan keyin qolganlari original counter bilan davom etadi. Immutable SQL guard nazoratsiz sealedSecret o‘zgarishini rad qiladi; tarixni mustaqil tahrirlash/o‘chirish rad, credential/factor cascade bilan o‘chirish mumkin. Actor UUID historical label sifatida saqlanadi; insertda haqiqiy faol grant talab qilinadi.

Kalit yo‘qolsa old ciphertextni taxmin qilish, default kalit yoki recovery bypass yo‘q. Mavjud verified password + bir martalik backup recovery faktorini revoke qilish yo‘li boshqa tartibda mavjud. Shifrlash key rotation **backupdan tiklangan eski counter/recovery code/sessionlarni xavfsiz qilmaydi**; restored credentials invalidation va operator authorization reconciliation alohida shart. Bu hujjat SEC-02.06ni o‘zi done qilmaydi.
